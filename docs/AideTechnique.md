## Liste de voyages

But : ne plus écrire les cartes à la main dans `App.jsx`, mais partir d'un
tableau.

- `src/data/trips.js` : tableau avec des voyages en dur pour tester (id, titre,
  dates, budget). Plus tard ça sera remplacé par un fetch vers l'API. Les dates
  sont en format `2027-03-10` (plus simple à comparer), je les reformate en
  `10/03/2027` seulement pour l'affichage.
- `Dashboard.jsx` : la page. Elle importe le tableau et fait
  `trips.map(trip => <TripCard key={trip.id} trip={trip} />)`.
  Le `.map` transforme chaque voyage en une carte.
- `key` : obligatoire dans un `.map`, doit être unique (j'utilise l'id). Ça
  permet à React de suivre chaque élément de la liste.
- `TripCard.jsx` : reçoit un `trip` en prop et l'affiche. Les props = les données
  que le parent passe à l'enfant.
- `App.jsx` : juste `<Navbar />` + `<Dashboard />`.

Organisation des dossiers :
- `pages/` = un écran entier
- `components/` = bouts réutilisables
- `data/` = les données

## Router

Avant, le passage liste <-> détail se faisait avec un `useState` dans `App.jsx`
(`selectedTripId`). Ça marchait mais pas d'URL, pas de bouton retour du
navigateur, impossible de partager un lien vers un voyage précis.

Remplacé par `react-router-dom` :
- `main.jsx` : `<App />` est mis dans un `<BrowserRouter>` (une seule fois, tout
  en haut de l'app).
- `App.jsx` : `<Routes>` avec une `<Route>` par page. `/` -> Dashboard,
  `/trips/:id` -> TripDetail. Le `:id` est un paramètre dynamique dans l'URL.
- `TripDetail.jsx` : ne reçoit plus le voyage en prop, il le retrouve lui-même
  avec `useParams()` qui lit le `:id` de l'URL, puis `trips.find(...)`.
  Attention : `id` récupéré dans l'URL est une string, il faut le passer en
  `Number()` avant de comparer.
- `Dashboard.jsx` / `Navbar.jsx` : les `onClick` / `<a href>` sont remplacés par
  des `<Link to="...">`. Avec `<Link>`, la page ne recharge pas (contrairement à
  un `<a>` classique), seul le contenu change.
- Piège rencontré : j'avais mis un `return` (cas "voyage introuvable") avant le
  `useState`. ESLint a bloqué ça : les Hooks doivent être appelés à chaque
  render, dans le même ordre, jamais après un `if`/`return`. Il faut mettre tous
  les `useState` tout en haut du composant.

## Supabase

Choix du back-end : Supabase (auth + base PostgreSQL déjà hébergées, pas de
serveur à écrire soi-même).

- Clés stockées dans `.env.local` (jamais commit, déjà dans le `.gitignore` via
  `*.local`) : `VITE_SUPABASE_URL` et `VITE_SUPABASE_PUBLISHABLE_KEY`. Le préfixe
  `VITE_` est obligatoire, sinon Vite n'expose pas la variable au code.
- `src/lib/supabaseClient.js` : crée la connexion une fois avec `createClient()`
  et l'exporte (`supabase`). Partout ailleurs on fait juste
  `import { supabase } from "../lib/supabaseClient"`.
- Pas besoin de table `users` perso : Supabase Auth gère déjà `auth.users`.

### Table `trips`

```sql
create table trips (
  id bigint generated by default as identity primary key,
  user_id uuid not null references auth.users(id) on delete cascade,
  titre text not null,
  date_debut date not null,
  date_fin date not null,
  budget_total numeric not null default 0,
  created_at timestamptz not null default now()
);

alter table trips enable row level security;

create policy "Un utilisateur gère ses propres voyages"
on trips
for all
using (auth.uid() = user_id)
with check (auth.uid() = user_id);
```

- `user_id` = clé étrangère vers `auth.users`, `on delete cascade` supprime les
  voyages si le compte est supprimé.
- RLS (Row Level Security) : par défaut personne ne peut lire/écrire dans une
  table Supabase depuis le front. Faut activer RLS puis créer une "policy" qui
  dit qui a le droit de faire quoi.
- La policy ici : chacun ne voit/modifie que ses propres lignes (`user_id =
  auth.uid()`, l'id de l'utilisateur connecté donné par Supabase). `using` pour
  lire/modifier/supprimer, `with check` pour la création. C'est ça qui rend
  l'anon/publishable key safe à mettre dans le front.

### Table `steps`

```sql
create table steps (
  id bigint generated by default as identity primary key,
  trip_id bigint not null references trips(id) on delete cascade,
  jour date not null,
  heure time,
  titre text not null,
  notes text,
  cout numeric not null default 0,
  latitude double precision,
  longitude double precision
);

alter table steps enable row level security;

create policy "Un utilisateur gère les étapes de ses propres voyages"
on steps
for all
using (
  exists (
    select 1 from trips
    where trips.id = steps.trip_id
    and trips.user_id = auth.uid()
  )
)
with check (
  exists (
    select 1 from trips
    where trips.id = steps.trip_id
    and trips.user_id = auth.uid()
  )
);
```

- `jour`/`heure`/`titre`/`notes`/`cout` reprennent les champs déjà utilisés dans
  `data/trips.js`. `latitude`/`longitude` sont prévus pour la carte plus tard
  (nullable, pas encore utilisés).
- `trip_id` : même principe que `user_id` sur `trips`, avec `on delete cascade`.
- Différence avec `trips` : `steps` n'a pas de `user_id` direct, donc la policy
  ne peut pas comparer directement. Elle fait une **sous-requête** (`exists`) :
  "est-ce qu'il existe un voyage dans `trips` qui a cet id (`trips.id =
  steps.trip_id`) ET qui appartient à l'utilisateur connecté
  (`trips.user_id = auth.uid()`) ?". Si oui, accès autorisé.

## Auth (savoir qui est connecté partout dans l'app)

Pour pas devoir redemander à Supabase "qui est connecté" dans chaque page, on
utilise le Context de React (`createContext`/`useContext`) : une valeur
accessible depuis n'importe quel composant sans la faire passer en props à
chaque niveau.

- `useEffect` : première fois que je l'utilise. Sert à lancer du code
  automatiquement à l'affichage du composant (ici : vérifier s'il y a déjà une
  session active). Le tableau `[]` à la fin veut dire "une seule fois, pas à
  chaque re-render".
- `onAuthStateChange` : écouteur qui se déclenche à chaque login/logout/etc,
  pour que le `user` reste à jour partout. Le `return () => ...unsubscribe()`
  dans le `useEffect` c'est le nettoyage, pour pas garder un écouteur qui tourne
  pour rien.

Fichiers, séparés en 3 (sinon eslint bloque le hot-reload, cf plus bas) :
- `context/authContext.js` : juste `createContext(null)`.
- `context/AuthContext.jsx` : le composant `AuthProvider`, contient toute la
  logique au-dessus.
- `hooks/useAuth.js` : `useContext(AuthContext)`, pour lire le user depuis
  n'importe quel composant avec juste `const { user } = useAuth()`.

Piège eslint : `react-refresh/only-export-components`. Un fichier ne peut
exporter QUE des composants (sinon le hot-reload de Vite pète). Comme
`AuthContext.jsx` exportait aussi `useAuth` (une fonction) et `AuthContext`
(un objet), fallait sortir les deux dans des fichiers à part.

`AuthProvider` doit envelopper `<App />` dans `main.jsx` pour que `useAuth()`
marche n'importe où dans l'appli (même logique que `BrowserRouter`).

## Page Login

`pages/Login.jsx` : formulaire avec inputs contrôlés (`value` + `onChange`
reliés à un `useState`, React garde la valeur au lieu du navigateur).

Deux pièges rencontrés :
- Le composant s'appelait `login` (minuscule) au lieu de `Login`. React exige
  une majuscule pour reconnaître un composant, sinon les Hooks (`useState`)
  plantent avec une erreur bizarre ("called in function that is neither a
  React function component...").
- `e.preventDefault()` obligatoire dans le submit, sinon le formulaire recharge
  la page (comportement HTML par défaut).
- Piège de validation : `type="email"` fait une validation native du
  navigateur. Si le texte tapé n'a pas la forme d'un email, le formulaire ne
  se soumet même pas (pas d'erreur, juste rien qui se passe) — normal, pas un
  bug côté code.

Ensuite branché à Supabase avec `supabase.auth.signInWithPassword({ email,
password })`. Cette fonction est `async`, faut mettre `await` devant (elle fait
un appel réseau, pas de réponse instantanée). Elle renvoie `{ data, error }` —
on récupère juste `error` : `null` si ça a marché, sinon on affiche
`error.message` dans un state dédié pour que l'utilisateur le voie à l'écran.
Si ça marche, `navigate("/")` (hook `useNavigate` de react-router) ramène au
dashboard.

## Page Signup

Quasi identique à Login, avec `supabase.auth.signUp` à la place. Différence :
pas de redirection automatique après — un state `success` remplace le
formulaire par un message ("vérifie ta boîte mail"), parce que selon la config
du projet Supabase la confirmation par email peut être obligatoire avant de
pouvoir se connecter.

`success ? <p>...</p> : <form>...</form>` : ternaire pour choisir quoi afficher,
comme un if/else mais utilisable directement dans le JSX.

## Navbar dynamique selon la connexion

`Navbar.jsx` utilise `useAuth()` pour savoir si quelqu'un est connecté
(`const { user } = useAuth()`, `null` si personne). Affiche email +
bouton déconnexion si connecté, sinon les liens Connexion/Inscription.

- `supabase.auth.signOut()` déconnecte. Pas besoin de remettre `user` à `null`
  à la main : le `onAuthStateChange` dans `AuthContext.jsx` le détecte et met
  à jour le state tout seul, partout dans l'app.
- `<>...</>` (Fragment) : pour grouper plusieurs éléments JSX sans ajouter de
  `<div>` inutile — une expression JSX doit avoir un seul élément racine.

## Dashboard branché sur les vraies données

`Dashboard.jsx` allait chercher les voyages dans `data/trips.js` (mock).
Remplacé par une vraie requête Supabase :

```js
const { data, error } = await supabase.from("trips").select("*");
```

- Pas besoin de filtrer sur `user_id` dans le code : la policy RLS mise en
  place sur la table `trips` le fait automatiquement, on ne peut recevoir que
  ses propres voyages.
- Piège `useEffect` : sa fonction ne peut pas être `async` directement. Solution
  : définir une fonction `async` à l'intérieur (`fetchTrips`) et l'appeler juste
  après.
- 2 states en plus : `loading` (affiche "Chargement..." pendant l'appel) et
  `trips` (rempli avec les données une fois la réponse arrivée).

Piège de nommage : les colonnes SQL sont en snake_case (`date_debut`,
`date_fin`, `budget_total`), pas en camelCase comme dans le mock. Supabase
renvoie les données avec exactement les noms de colonnes de la table. Fallu
adapter `TripCard.jsx` (`trip.date_debut` au lieu de `trip.dateDebut`, etc).

## GRANT vs RLS

Erreur rencontrée en créant le premier voyage : `permission denied for table
trips`. Pas une erreur RLS (celle-là dit "new row violates row-level security
policy"), mais une couche encore avant : le rôle `authenticated` n'avait tout
simplement pas le droit de toucher la table, indépendamment des lignes.

- **GRANT** = le rôle a-t-il le droit de faire ça sur la table, en général.
- **RLS/policy** = d'accord il a le droit, mais sur quelles lignes précisément.

Supabase configure ça normalement tout seul, mais il a fallu l'ajouter à la
main :
```sql
grant select, insert, update, delete on trips to authenticated;
grant select, insert, update, delete on steps to authenticated;
grant usage, select on sequence trips_id_seq to authenticated;
grant usage, select on sequence steps_id_seq to authenticated;
```
(les grants sur les sequences sont nécessaires parce que `id` est auto-généré)

## Formulaire de création de voyage

`pages/NewTrip.jsx` : un seul state objet pour les 4 champs du formulaire,
au lieu d'un `useState` par champ :
```js
const [form, setForm] = useState({ titre: "", date_debut: "", date_fin: "", budget_total: "" });

function handleChange(e) {
  setForm({ ...form, [e.target.name]: e.target.value });
}
```
- `[e.target.name]` : nom de propriété calculé à partir de l'attribut `name` de
  l'input. Chaque input a `name="..."` + `value`/`onChange` partagés.
- `{ ...form, ... }` : jamais modifier le state directement, on recopie tout
  et on écrase juste le champ concerné.
- `user_id: user.id` (via `useAuth()`) ajouté à la volée avant l'insert, sinon
  la policy RLS refuse (elle attend `user_id = auth.uid()`).

Piège de routing : le chemin dans `<Route path="...">` et celui dans
`<Link to="...">` doivent être identiques caractère pour caractère
(`/trips/new` partout, pas `/trip/new` d'un côté).

## TripDetail branché sur les vraies données

Même principe que Dashboard, mais avec 2 nouveautés :

- **Requête avec jointure** : `supabase.from("trips").select("*, steps(*)").eq("id", id).single()`.
  Grâce à la clé étrangère `steps.trip_id -> trips.id`, Supabase remonte les
  steps du voyage directement dans `data.steps`, en une seule requête.
  `.eq(...)` filtre par id, `.single()` dit qu'on attend un seul résultat (pas
  un tableau).
- **`useEffect(..., [id])`** au lieu de `[]` : si on navigue d'un voyage à
  l'autre sans que le composant soit détruit/recréé par React Router, il faut
  quand même relancer la requête. Avec `id` en dépendance, l'effet se
  redéclenche à chaque changement d'id dans l'URL.

`data/trips.js` (le mock) n'est plus utilisé nulle part depuis cette étape.
