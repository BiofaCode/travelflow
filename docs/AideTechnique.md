## Liste de voyages

But : ne plus écrire les cartes à la main dans `App.jsx`, mais partir d'un
tableau.

- `src/data/trips.js` : tableau avec des voyages en dur pour tester (id, titre,
  dates, budget). Plus tard ça sera remplacé par un fetch vers l'API. Les dates
  sont en format `2027-03-10` (plus simple à comparer), je les reformate en
  `10/03/2027` seulement pour l'affichage.
- `Dashboard.jsx` : la page. Elle importe le tableau et fait
  `trips.map(trip => <TripCard key={trip.id} trip={trip} />)`.
  Le `.map` transforme chaque voyage en une carte.
- `key` : obligatoire dans un `.map`, doit être unique (j'utilise l'id). Ça
  permet à React de suivre chaque élément de la liste.
- `TripCard.jsx` : reçoit un `trip` en prop et l'affiche. Les props = les données
  que le parent passe à l'enfant.
- `App.jsx` : juste `<Navbar />` + `<Dashboard />`.

Organisation des dossiers :
- `pages/` = un écran entier
- `components/` = bouts réutilisables
- `data/` = les données

## Router

Avant, le passage liste <-> détail se faisait avec un `useState` dans `App.jsx`
(`selectedTripId`). Ça marchait mais pas d'URL, pas de bouton retour du
navigateur, impossible de partager un lien vers un voyage précis.

Remplacé par `react-router-dom` :
- `main.jsx` : `<App />` est mis dans un `<BrowserRouter>` (une seule fois, tout
  en haut de l'app).
- `App.jsx` : `<Routes>` avec une `<Route>` par page. `/` -> Dashboard,
  `/trips/:id` -> TripDetail. Le `:id` est un paramètre dynamique dans l'URL.
- `TripDetail.jsx` : ne reçoit plus le voyage en prop, il le retrouve lui-même
  avec `useParams()` qui lit le `:id` de l'URL, puis `trips.find(...)`.
  Attention : `id` récupéré dans l'URL est une string, il faut le passer en
  `Number()` avant de comparer.
- `Dashboard.jsx` / `Navbar.jsx` : les `onClick` / `<a href>` sont remplacés par
  des `<Link to="...">`. Avec `<Link>`, la page ne recharge pas (contrairement à
  un `<a>` classique), seul le contenu change.
- Piège rencontré : j'avais mis un `return` (cas "voyage introuvable") avant le
  `useState`. ESLint a bloqué ça : les Hooks doivent être appelés à chaque
  render, dans le même ordre, jamais après un `if`/`return`. Il faut mettre tous
  les `useState` tout en haut du composant.

## Supabase

Choix du back-end : Supabase (auth + base PostgreSQL déjà hébergées, pas de
serveur à écrire soi-même).

- Clés stockées dans `.env.local` (jamais commit, déjà dans le `.gitignore` via
  `*.local`) : `VITE_SUPABASE_URL` et `VITE_SUPABASE_PUBLISHABLE_KEY`. Le préfixe
  `VITE_` est obligatoire, sinon Vite n'expose pas la variable au code.
- `src/lib/supabaseClient.js` : crée la connexion une fois avec `createClient()`
  et l'exporte (`supabase`). Partout ailleurs on fait juste
  `import { supabase } from "../lib/supabaseClient"`.
- Pas besoin de table `users` perso : Supabase Auth gère déjà `auth.users`.

### Table `trips`

```sql
create table trips (
  id bigint generated by default as identity primary key,
  user_id uuid not null references auth.users(id) on delete cascade,
  titre text not null,
  date_debut date not null,
  date_fin date not null,
  budget_total numeric not null default 0,
  created_at timestamptz not null default now()
);

alter table trips enable row level security;

create policy "Un utilisateur gère ses propres voyages"
on trips
for all
using (auth.uid() = user_id)
with check (auth.uid() = user_id);
```

- `user_id` = clé étrangère vers `auth.users`, `on delete cascade` supprime les
  voyages si le compte est supprimé.
- RLS (Row Level Security) : par défaut personne ne peut lire/écrire dans une
  table Supabase depuis le front. Faut activer RLS puis créer une "policy" qui
  dit qui a le droit de faire quoi.
- La policy ici : chacun ne voit/modifie que ses propres lignes (`user_id =
  auth.uid()`, l'id de l'utilisateur connecté donné par Supabase). `using` pour
  lire/modifier/supprimer, `with check` pour la création. C'est ça qui rend
  l'anon/publishable key safe à mettre dans le front.

### Table `steps`

```sql
create table steps (
  id bigint generated by default as identity primary key,
  trip_id bigint not null references trips(id) on delete cascade,
  jour date not null,
  heure time,
  titre text not null,
  notes text,
  cout numeric not null default 0,
  latitude double precision,
  longitude double precision
);

alter table steps enable row level security;

create policy "Un utilisateur gère les étapes de ses propres voyages"
on steps
for all
using (
  exists (
    select 1 from trips
    where trips.id = steps.trip_id
    and trips.user_id = auth.uid()
  )
)
with check (
  exists (
    select 1 from trips
    where trips.id = steps.trip_id
    and trips.user_id = auth.uid()
  )
);
```

- `jour`/`heure`/`titre`/`notes`/`cout` reprennent les champs déjà utilisés dans
  `data/trips.js`. `latitude`/`longitude` sont prévus pour la carte plus tard
  (nullable, pas encore utilisés).
- `trip_id` : même principe que `user_id` sur `trips`, avec `on delete cascade`.
- Différence avec `trips` : `steps` n'a pas de `user_id` direct, donc la policy
  ne peut pas comparer directement. Elle fait une **sous-requête** (`exists`) :
  "est-ce qu'il existe un voyage dans `trips` qui a cet id (`trips.id =
  steps.trip_id`) ET qui appartient à l'utilisateur connecté
  (`trips.user_id = auth.uid()`) ?". Si oui, accès autorisé.

## Auth (savoir qui est connecté partout dans l'app)

Pour pas devoir redemander à Supabase "qui est connecté" dans chaque page, on
utilise le Context de React (`createContext`/`useContext`) : une valeur
accessible depuis n'importe quel composant sans la faire passer en props à
chaque niveau.

- `useEffect` : première fois que je l'utilise. Sert à lancer du code
  automatiquement à l'affichage du composant (ici : vérifier s'il y a déjà une
  session active). Le tableau `[]` à la fin veut dire "une seule fois, pas à
  chaque re-render".
- `onAuthStateChange` : écouteur qui se déclenche à chaque login/logout/etc,
  pour que le `user` reste à jour partout. Le `return () => ...unsubscribe()`
  dans le `useEffect` c'est le nettoyage, pour pas garder un écouteur qui tourne
  pour rien.

Fichiers, séparés en 3 (sinon eslint bloque le hot-reload, cf plus bas) :
- `context/authContext.js` : juste `createContext(null)`.
- `context/AuthContext.jsx` : le composant `AuthProvider`, contient toute la
  logique au-dessus.
- `hooks/useAuth.js` : `useContext(AuthContext)`, pour lire le user depuis
  n'importe quel composant avec juste `const { user } = useAuth()`.

Piège eslint : `react-refresh/only-export-components`. Un fichier ne peut
exporter QUE des composants (sinon le hot-reload de Vite pète). Comme
`AuthContext.jsx` exportait aussi `useAuth` (une fonction) et `AuthContext`
(un objet), fallait sortir les deux dans des fichiers à part.

`AuthProvider` doit envelopper `<App />` dans `main.jsx` pour que `useAuth()`
marche n'importe où dans l'appli (même logique que `BrowserRouter`).

## Page Login

`pages/Login.jsx` : formulaire avec inputs contrôlés (`value` + `onChange`
reliés à un `useState`, React garde la valeur au lieu du navigateur).

Deux pièges rencontrés :
- Le composant s'appelait `login` (minuscule) au lieu de `Login`. React exige
  une majuscule pour reconnaître un composant, sinon les Hooks (`useState`)
  plantent avec une erreur bizarre ("called in function that is neither a
  React function component...").
- `e.preventDefault()` obligatoire dans le submit, sinon le formulaire recharge
  la page (comportement HTML par défaut).
- Piège de validation : `type="email"` fait une validation native du
  navigateur. Si le texte tapé n'a pas la forme d'un email, le formulaire ne
  se soumet même pas (pas d'erreur, juste rien qui se passe) — normal, pas un
  bug côté code.

Ensuite branché à Supabase avec `supabase.auth.signInWithPassword({ email,
password })`. Cette fonction est `async`, faut mettre `await` devant (elle fait
un appel réseau, pas de réponse instantanée). Elle renvoie `{ data, error }` —
on récupère juste `error` : `null` si ça a marché, sinon on affiche
`error.message` dans un state dédié pour que l'utilisateur le voie à l'écran.
Si ça marche, `navigate("/")` (hook `useNavigate` de react-router) ramène au
dashboard.

## Page Signup

Quasi identique à Login, avec `supabase.auth.signUp` à la place. Différence :

`success ? <p>...</p> : <form>...</form>` : ternaire pour choisir quoi afficher,

## Dashboard branché sur les vraies données

`Dashboard.jsx` allait chercher les voyages dans `data/trips.js` (mock).
Remplacé par une vraie requête Supabase :

```js
const { data, error } = await supabase.from("trips").select("*");
```

- Pas besoin de filtrer sur `user_id` dans le code : la policy RLS mise en

  ses propres voyages.
- Piège `useEffect` : sa fonction ne peut pas être `async` directement. Solution

Piège de nommage : les colonnes SQL sont en snake_case (`date_debut`,
`date_fin`, `budget_total`), pas en camelCase comme dans le mock. Supabase
renvoie les données avec exactement les noms de colonnes de la table. Fallu
adapter `TripCard.jsx` (`trip.date_debut` au lieu de `trip.dateDebut`, etc).

## GRANT vs RLS

Erreur rencontrée en créant le premier voyage : `permission denied for table
trips`. Pas une erreur RLS (celle-là dit "new row violates row-level security
policy"), mais une couche encore avant : le rôle `authenticated` n'avait tout
simplement pas le droit de toucher la table, indépendamment des lignes.

- **GRANT** = le rôle a-t-il le droit de faire ça sur la table, en général.
- **RLS/policy** = d'accord il a le droit, mais sur quelles lignes précisément.

Supabase configure ça normalement tout seul, mais il a fallu l'ajouter à la
main :
```sql
grant select, insert, update, delete on trips to authenticated;
grant select, insert, update, delete on steps to authenticated;
grant usage, select on sequence trips_id_seq to authenticated;
grant usage, select on sequence steps_id_seq to authenticated;
```
(les grants sur les sequences sont nécessaires parce que `id` est auto-généré)

## Formulaire de création de voyage

`pages/NewTrip.jsx` : un seul state objet pour les 4 champs du formulaire,
au lieu d'un `useState` par champ :
```js
const [form, setForm] = useState({ titre: "", date_debut: "", date_fin: "", budget_total: "" });

function handleChange(e) {
  setForm({ ...form, [e.target.name]: e.target.value });
}
```
- `[e.target.name]` : nom de propriété calculé à partir de l'attribut `name` de
  l'input. Chaque input a `name="..."` + `value`/`onChange` partagés.
- `{ ...form, ... }` : jamais modifier le state directement, on recopie tout
  et on écrase juste le champ concerné.
- `user_id: user.id` (via `useAuth()`) ajouté à la volée avant l'insert, sinon
  la policy RLS refuse (elle attend `user_id = auth.uid()`).

Piège de routing : le chemin dans `<Route path="...">` et celui dans
`<Link to="...">` doivent être identiques caractère pour caractère
(`/trips/new` partout, pas `/trip/new` d'un côté).

## TripDetail branché sur les vraies données

Même principe que Dashboard, mais avec 2 nouveautés :

- **Requête avec jointure** : `supabase.from("trips").select("*, steps(*)").eq("id", id).single()`.
  Grâce à la clé étrangère `steps.trip_id -> trips.id`, Supabase remonte les
  steps du voyage directement dans `data.steps`, en une seule requête.
  `.eq(...)` filtre par id, `.single()` dit qu'on attend un seul résultat (pas
  un tableau).
- **`useEffect(..., [id])`** au lieu de `[]` : si on navigue d'un voyage à
  l'autre sans que le composant soit détruit/recréé par React Router, il faut
  quand même relancer la requête. Avec `id` en dépendance, l'effet se
  redéclenche à chaque changement d'id dans l'URL.

`data/trips.js` (le mock) n'est plus utilisé nulle part depuis cette étape.

## Supprimer un voyage

Bouton dans `TripDetail.jsx` :
```js
async function handleDelete() {
  const confirme = window.confirm("Supprimer ce voyage définitivement ?");
  if (!confirme) return;

  const { error } = await supabase.from("trips").delete().eq("id", id);
  ...
  navigate("/");
}
```
- `window.confirm(...)` : boîte de dialogue native du navigateur, renvoie
  `true`/`false` selon le bouton cliqué.
- `.delete().eq("id", id)` : supprime la ligne avec cet id. La RLS s'applique
  aussi ici, donc impossible de supprimer le voyage de quelqu'un d'autre même
  en trafiquant la requête.
- Grâce au `on delete cascade` mis sur `steps.trip_id` en créant la table, les
  steps du voyage sont supprimées automatiquement, pas besoin de le faire à la
  main.

## Modifier un voyage

`pages/EditTrip.jsx` : même formulaire que `NewTrip`, mais en 2 temps.

- `form` démarre à `null` (pas un objet vide) le temps de charger le voyage
  existant via un `useEffect`. `if (!form) return <p>Chargement...</p>` évite
  de planter en lisant `form.titre` avant que la réponse arrive.
- `.update({ ... }).eq("id", id)` au lieu de `.insert()` : modifie la ligne
  existante plutôt que d'en créer une nouvelle.
- Redirige vers `/trips/:id` (le détail) après sauvegarde, pas vers `/`.

## Ajouter une étape

Formulaire ajouté directement dans `TripDetail.jsx` (pas une page séparée),
avec son propre state `newStep` (même pattern objet + `handleChange`
générique que les autres formulaires).

- `min={trip.date_debut}` / `max={trip.date_fin}` sur l'input `type="date"` :
  empêche de choisir une date hors des dates du voyage, directement géré par
  le navigateur.
- Après l'insert dans `steps`, on refait la requête `trips` +
  `select("*, steps(*)")` pour récupérer la liste à jour, plutôt que de
  recharger toute la page.
- `setJourActif(newStep.jour)` juste après : bascule automatiquement sur
  l'onglet du jour où l'étape vient d'être ajoutée, pour la voir tout de suite
  (même si c'est un nouveau jour qui n'avait pas encore d'onglet).
- `required` sur les champs titre/jour : validation native du navigateur
  (même mécanisme que `type="email"` vu avant, bloque silencieusement si
  vide).

## Supprimer une étape

`StepItem` reste un composant "muet" (juste de l'affichage) : il reçoit une
fonction `onDelete` en prop et se contente de l'appeler au clic
(`onClick={() => onDelete(step.id)}`). La vraie logique (confirmation, appel
Supabase) reste dans `TripDetail`, qui la passe en prop — même principe de
"remonter l'état" que `Dashboard`/`onSelectTrip` au tout début du projet.

Piège eslint (react-hooks v7) : appeler depuis un `useEffect` une fonction
définie ailleurs dans le composant (donc pas locale à l'effet) qui fait du
`setState` est maintenant averti/bloqué (`react-hooks/set-state-in-effect` +
`exhaustive-deps`). Du coup 2 fonctions séparées :
- le `fetchTrip` imbriqué **dans** le `useEffect`, pour le chargement initial
  (inchangé depuis le début) ;
- un `refreshTrip` à part, appelé seulement depuis `handleAddStep` et
  `handleDeleteStep` (jamais depuis un `useEffect`).

Légère duplication de la requête entre les deux, mais plus simple que de
sacrifier au `useCallback`/dépendances pour un seul composant.

## Carte Leaflet

## Budget (barre de progression)

Dernière fonctionnalité du MVP. Pas de nouvelle requête Supabase ni de colonne
en plus : le total dépensé se calcule à partir de `trip.steps`, déjà chargé.

```js
const totalDepense = trip.steps.reduce((somme, step) => somme + step.cout, 0);
```
`.reduce()` : transforme un tableau en une seule valeur. `0` = valeur de
départ, puis à chaque étape `somme + step.cout` devient la nouvelle somme.

`components/BudgetBar.jsx` : composant à part (réutilisable), reçoit juste
`depense` et `budget` en props.
- `Math.min((depense / budget) * 100, 100)` : plafonne à 100% pour que la barre
  ne déborde pas si le budget est dépassé.
- Largeur de la barre en `style={{ width: ... }}` plutôt qu'en classe Tailwind :
  seul moyen d'avoir un pourcentage calculé dynamiquement (Tailwind ne peut
  générer que des classes connues à l'avance).
- Couleur rouge + message si `depense > budget`.

Réactif "gratuitement" : comme c'est calculé à chaque rendu à partir de
`trip.steps`, ajouter/supprimer une étape met à jour la barre automatiquement,
sans code spécifique pour ça.

## Refonte visuelle (thème sombre)

Inspiré de Wanderlog/TripkyGo, mais en gardant le scope raisonnable (pas d'IA,
pas de recherche de lieu, pas de photos/réservations — juste le visuel et la
structure).

- **Police** : Plus Jakarta Sans (Google Fonts), chargée via `<link>` dans
  `index.html` (2 `<link rel="preconnect">` pour accélérer le chargement, puis
  le lien vers le CSS de la police). Appliquée globalement dans `index.css`
  via `font-family` sur `body`.
- **Palette** : fini le blanc/gris clair, tout en `slate-950` (fond),
  `slate-900` (cartes), `slate-800` (bordures), `slate-100`/`slate-400`
  (texte), et **rose-500** comme couleur d'accent (remplace le bleu partout :
  boutons, liens, prix).
- **`color-scheme: dark`** dans `index.css` (sur `body`) : indispensable avec
  des inputs natifs (`date`, `number`, `time`). Sans ça, les icônes/texte de
  ces champs restent calés sur un rendu "fond clair" du navigateur et
  deviennent presque invisibles sur fond sombre. Piège facile à louper.
- **Carte Leaflet** : essayé d'abord des tuiles sombres CartoDB
  (`basemaps.cartocdn.com/dark_all/...`) — **erreur "API key required"**,
  CARTO a changé sa politique, ce n'est plus libre d'accès comme avant.
  Reviendu aux vraies tuiles OpenStreetMap standard (gratuites, sans clé,
  conforme au cahier des charges), et simulé l'effet sombre avec un **filtre
  CSS** sur les tuiles (`.map-tiles-dark` dans `index.css`) :
  ```css
  filter: invert(1) hue-rotate(180deg) brightness(0.95) contrast(0.9);
  ```
  `invert(1)` retourne toutes les couleurs (noir ↔ blanc), `hue-rotate(180deg)`
  corrige les teintes que l'inversion fausse (sinon l'eau bleue devient
  orange), `brightness`/`contrast` ajustent le rendu. Appliqué uniquement aux
  tuiles via la prop `className` du `<TileLayer>` — les marqueurs/popups
  vivent dans des calques Leaflet séparés, donc pas affectés par le filtre
  (toujours de vraies couleurs).
- **Leçon retenue** : vérifier qu'un service tiers "gratuit" l'est vraiment
  avant de l'utiliser, plutôt que de faire confiance à une supposition.

Au début pas de bascule clair/sombre (un seul thème). Ajoutée plus tard, voir
"Mode clair / sombre" plus bas.

- **A (fait)** : colonne `destination` (text, nullable) ajoutée à `trips` en
  SQL, champ ajouté dans `NewTrip`/`EditTrip`, affiché sur `TripCard` et
  `TripDetail`. `data.destination || ""` dans `EditTrip` : les voyages créés
  avant ce champ ont `destination = null` en base, il faut l'intercepter avant
  de le mettre dans un input contrôlé (même piège que vu avant pour
  latitude/longitude).
- **B (fait)** : géocoder la destination avec **Nominatim** (recherche OSM
  gratuite, pas de clé) pour obtenir un point central.
  - `lib/nominatim.js` : `geocodeDestination(destination)`, un simple
    `fetch` vers `nominatim.openstreetmap.org/search?q=...&format=json`.
    Teste bien avant de coder dedans avec `curl` pour vérifier le format de
    réponse (lat/lon renvoyés en **strings**, fallu les passer en `Number()`).
  - Dans `TripDetail.jsx`, un **2ᵉ `useEffect`** séparé (pas mélangé avec celui
    du chargement du voyage), dépendant de `trip?.destination` seulement (pas
    de tout l'objet `trip`) pour éviter de re-géocoder à chaque rafraîchissement
    après ajout/suppression d'étape.
  - Piège eslint rencontré : un `setState` **synchrone** (pas dans un
    `.then()`) directement dans le corps d'un effet est maintenant bloqué
    (`react-hooks/set-state-in-effect`), même pour un simple `return` anticipé
    qui remettait le state à `null`. Solution : un `return;` tout court sans
    toucher au state si rien à géocoder — seul le `setState` dans le callback
    asynchrone (`.then(...)`) est autorisé.
  - **Bonus visible tout de suite** : `TripMap` accepte maintenant une prop
    `centreDestination` — si aucune étape n'a encore de coordonnées, la carte
    se centre quand même sur la destination géocodée plutôt que d'afficher
    juste du texte. Zoom moins serré (10 au lieu de 12) dans ce cas, vu qu'on
    n'a qu'un point large (la ville), pas un lieu précis.
- **C (fait, mais pas avec Overpass)** : au début prévu avec **Overpass API**
  (requêtes sur la base OSM). En testant : erreurs 406, 502 et timeouts très
  souvent, le serveur public est saturé. Pas fiable pour une démo.
  Remplacé par l'**API de recherche de Wikipédia** (gratuite, sans clé,
  `origin=*` pour que le navigateur ait le droit de l'appeler) :
  - `gsrsearch: "nearcoord:8km,lat,lon"` = pages Wikipédia autour du point,
    classées par pertinence, donc les lieux connus sortent en premier.
  - Première version avec `geosearch` : que des trucs au hasard juste à côté
    (arrêts de bus, rues...). Et `colimit` par défaut = 10, donc la plupart des
    pages n'avaient pas de coordonnées → fallu mettre `colimit: "max"`.
  - Filtre avec 2 regex : ce qui ressemble à un lieu (musée, église, parc...)
    et ce qu'on exclut (clubs, batailles, gares, universités...). Piège :
    `tour` matchait "Tourisme", corrigé avec `tour`.
  - On cherche en **français ET en anglais** (`Promise.allSettled`, si une
    langue plante on garde l'autre), parce qu'en français c'est vide hors
    francophonie (Tokyo : presque rien). On enlève les doublons (même endroit à
    ~150 m près).
  - Testé : Rome 24 lieux, Lisbonne 13, Tokyo 7.

## Grosse refonte (design + fonctionnalités)

Fait en découpant le travail en 3 parties en parallèle (carte/API, design,
fonctionnalités), chacune sur des fichiers différents pour pas se marcher
dessus. Avant de commencer on a fixé les props que les composants se passent
(ex : ce que `TripDetail` donne à `TripMap`), comme ça chaque partie pouvait
avancer sans attendre l'autre.

### Nouveaux petits fichiers utilitaires
- `lib/dates.js` : `formatDate`, `formatJourCourt` ("mer. 10 mars"),
  `listerJours(debut, fin)` (tous les jours du voyage), `aujourdhui()`. Tout
  en **UTC** sinon selon le fuseau horaire une date peut reculer d'un jour.
- `lib/format.js` : `formatCHF` (séparateur de milliers suisse) et
  `formatHeure` (Postgres renvoie "09:30:00", on garde "09:30").
- Classes dans `index.css` avec `@apply` (`.card`, `.input`, `.label`,
  `.btn-primary`...) : avant chaque input avait 10 classes Tailwind copiées
  collées partout, maintenant une seule.

### Page d'un voyage
- Planning à gauche, carte à droite (sur mobile la carte passe au-dessus avec
  `order-first`). Onglets **Planning / Explorer / Budget**.
- Les onglets de jours affichent **tous** les jours du voyage (`listerJours`)
  et plus seulement ceux qui ont déjà des étapes.
- Le jour actif est **dérivé** au lieu d'être mis à jour dans un effet :
  ```js
  const jourActif = jours.includes(jourChoisi) ? jourChoisi : jours[0];
  ```
  Pas de `setState` dans un `useEffect` → eslint content, et c'est plus simple.
- Plus de latitude/longitude à taper : on clique sur la carte
  (`useMapEvents` de react-leaflet) ou on ajoute un lieu depuis Explorer.
- Modifier une étape : même formulaire, en mode édition (`update` au lieu de
  `insert`). Changer le jour dans le select = déplacer l'étape.
- Menu "..." : dupliquer le voyage (insert du voyage puis de ses étapes),
  imprimer (`window.print()` + classes `print:hidden` / `hidden print:block`
  de Tailwind pour n'imprimer que l'itinéraire), copier le lien.
- Dans `App.jsx`, `<TripDetail key={id} />` : quand on passe d'un voyage à un
  autre (après "Dupliquer" par ex.), React garde le même composant et donc les
  anciens states. Avec une `key` différente il le recrée à zéro.

### Carte
- Marqueurs numérotés pour le jour choisi (`L.divIcon` avec du HTML),
  reliés par une `Polyline` dans l'ordre des heures. Les autres jours en petits
  cercles gris.
- Recadrage automatique : petit composant enfant qui utilise `useMap()` et
  fait `fitBounds` sur les points. Il ne recadre que si le jour ou le nombre de
  points change, sinon la carte bougerait à chaque clic.
- Une carte globale sur le Dashboard avec toutes les étapes de tous les voyages.

### Dashboard
- Bug corrigé : le nombre d'étapes était toujours 0 parce qu'on faisait
  `select("*")`. Maintenant `select("*, steps(cout, latitude, longitude)")`.
- Stats, sections "À venir" / "Passés", recherche et tri.

### Accueil (style TripkyGo)
- Page publique si on n'est pas connecté (`/` affiche `Home` ou `Dashboard`
  selon `useAuth`). Mise en page inspirée de TripkyGo mais illustration et
  textes faits par nous (pas le droit de reprendre leurs images).
- `RequireAuth` : composant qui renvoie vers `/login` si pas connecté, posé
  autour des pages privées dans `App.jsx`.

### Performances
- `React.lazy` + `Suspense` sur `TripDetail` et la carte du Dashboard :
  Leaflet est lourd (~160 ko), il n'est chargé que quand on en a besoin. Dans
  le build on voit bien un fichier `TripDetail-xxx.js` séparé.

## Autocomplétion de la destination

Quand on tape "to" on veut voir Tokyo, Toronto, Toscane... Nominatim n'est pas
fait pour ça (et il demande max 1 requête par seconde). On utilise **Photon**
(photon.komoot.io), c'est aussi basé sur OpenStreetMap, gratuit, sans clé, et
fait exprès pour l'autocomplétion.

- `lib/photon.js` : `suggererDestinations(texte)` → `{ nom, detail, type, lat, lon, label }`.
  `lang=fr` pour avoir "Italie" et pas "Italia", `osm_tag=place` pour garder
  seulement les villes / pays / régions (pas les gares ou les magasins).
- `components/DestinationInput.jsx` : l'input avec la liste déroulante.
  - On attend **300 ms** sans frappe avant de chercher (`setTimeout` dans
    l'effet + `clearTimeout` dans le cleanup). Sinon une requête par lettre.
  - `AbortController` pour annuler l'ancienne requête si on retape entre-temps,
    sinon une vieille réponse peut arriver après la nouvelle et l'écraser.
  - Flèches haut/bas + Entrée + Échap au clavier, `role="combobox"` pour les
    lecteurs d'écran.
- Utilisé dans la barre de création et dans le formulaire de modification.

## Création de voyage façon TripkyGo

Une seule barre : **destination, dates, voyageurs, Créer**. Le titre est
généré ("Voyage à Rome") et le budget vaut 0, on les change après dans
"Modifier". Plus rapide que l'ancien formulaire avec 5 champs.

- `TripSearchBar.jsx` : la barre, utilisée sur l'accueil et sur `/trips/new`.
  Depuis l'accueil on passe les valeurs dans l'URL
  (`/trips/new?destination=Rome&debut=...&voyageurs=2`) et `NewTrip` les relit
  avec `useSearchParams`.
- `VoyageursInput.jsx` : compteur avec boutons − / + (entre 1 et 20).
- Nouvelle colonne en base :
  ```sql
  alter table trips add column voyageurs integer not null default 1;
  ```
  `default 1` : les voyages déjà créés ont automatiquement 1 voyageur.
- Dans l'onglet Budget : budget et dépenses **par personne** quand on est
  plusieurs.

## Plus d'activités dans Explorer

- Filtres élargis (stades, brasseries, quartiers, points de vue...) et rayon
  de 10 km.
- Chaque lieu a une **catégorie** (musée, monument, religieux, nature,
  loisirs) trouvée avec des regex sur la description → filtres en pilules.
- **Recherche par mot-clé** : `"voiture nearcoord:15km,lat,lon"`. Là on ne

## Mode clair / sombre

Tout le site est écrit avec des classes `slate-*` (`bg-slate-950`,
`text-slate-100`...). Réécrire chaque composant avec `dark:` partout aurait
été énorme. L'astuce : en **Tailwind v4** chaque couleur est une variable CSS
(`--color-slate-950`...). En mode clair, on **inverse l'échelle** dans
`index.css` :

```css
:root.light {
  --color-slate-950: #f4f6fb; /* le fond devient clair */
  --color-slate-100: #0f172a; /* le texte devient foncé */
  /* ... */
}
```

Du coup `bg-slate-950` = fond foncé en sombre, fond clair en clair, sans
toucher aux composants.

- Seuls pièges : les `text-white` posés sur le fond de page (devenus blanc sur
  blanc) → remplacés par `text-slate-50`. Le blanc sur un dégradé rose reste
  `text-white`.
- Le choix est gardé dans `localStorage`. Un petit script dans `index.html`
  pose la classe `light` **avant** que React démarre, sinon on voit un flash
  sombre au chargement. Par défaut on suit le réglage de l'ordi
  (`prefers-color-scheme`).
- Carte : en clair on enlève le filtre `invert` sur les tuiles.
- `hooks/useTheme.js` : il y a deux boutons (navbar + menu mobile), il faut
  qu'ils soient toujours d'accord → `useSyncExternalStore` qui écoute la classe
  de `<html>` au lieu d'un `useState` dans chaque bouton.

## Carte plus jolie (fonds Esri)

L'ancien rendu (tuiles OSM + filtre `invert` en CSS) faisait des couleurs un
peu bizarres. Retesté CARTO : toujours une image "API KEY REQUIRED" à la place
des tuiles (on l'a vu en ouvrant l'image téléchargée avec `curl`, le code HTTP
était 200 donc on ne le voit pas sans regarder l'image !).

Pris les fonds **Esri** (gratuits, sans clé, juste l'attribution à afficher) :
- sombre : `Canvas/World_Dark_Gray_Base` + une 2e couche
  `World_Dark_Gray_Reference` par-dessus qui contient seulement les noms
  (rues, villes). Deux `<TileLayer>` l'un sur l'autre.
- clair : `World_Street_Map`, plus coloré.
- `components/FondCarte.jsx` choisit selon le thème (`useTheme`), utilisé par
  `TripMap` et `DashboardMap`. Attention l'ordre est `{z}/{y}/{x}` chez Esri
  (et pas `{z}/{x}/{y}` comme OSM).

Marqueurs en forme d'épingle : un carré avec 3 coins arrondis tourné de 45°
(`.carte-pin` dans `index.css`), le numéro à l'intérieur tourné dans l'autre
sens pour rester droit. Le trajet du jour = 2 `Polyline` : une large et
transparente (halo) + une fine en pointillés.

## Suggestions de lieux dans le titre d'une étape

Quand on clique dans le titre du formulaire d'étape, ça propose direct les
lieux populaires (ceux de Wikipédia). Si on tape, ça cherche autour de la
destination avec **Photon** (`suggererLieuxProches` dans `lib/photon.js`) :
"colis" → Colisée, "musee" → les musées de Rome, "pizza" → les pizzerias.
- `lat` et `lon` dans l'URL : Photon met en avant ce qui est proche.
- On jette ce qui est à plus de ~50 km (homonyme dans un autre pays) et les
  doublons (Photon renvoie souvent le bâtiment + le point).
- En choisissant un lieu, le titre ET la position sont remplis → l'épingle
  apparaît sur la carte sans avoir à cliquer.

Réutilisé le même composant que pour la destination (`DestinationInput`) en
lui ajoutant 2 props : `rechercher` (quelle fonction de recherche utiliser) et
`suggestionsVides` (ce qu'on montre avant de taper). Piège : la fonction
passée dans `rechercher` doit être dans un `useCallback`, sinon elle change à
chaque render et l'effet de recherche se relance en boucle.
